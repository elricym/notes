## 一段话总结

Claude 写代码太快，Anthropic 的瓶颈从"写代码"变成了源码管理、构建和 CI 这些按人类规模设计的基础设施。每天合并的代码变更从 5 月约 2,500 次涨到 9 月 3 万多次后，他们用 5 个月自研了版本控制系统 **Scion**，把 monorepo 从 git 完整迁走，同时还做了代码审查工具 Antique、代码搜索和源码权限系统。核心思路：客户端（agent 和任务）永远在线，所以把计算放到服务端，客户端只按需拉取数据。

## 关键数字

- 日合并变更：2026 年 5 月约 2,500 → 9 月 30,000+（10 倍以上）
- main 分支历史近 100 GB，压缩后的工作副本超 25 GB
- CI 每天约 2,500 万次代码检出；若直接用 git 拉取，每天超 600 PB 流量
- 高峰期运营了几百个内部 git 镜像
- 团队 7 人，5 个月建成 Scion + Antique 等并完成迁移
- 结果：基础设施 CPU/内存占用比原 git 镜像小 200 倍；检出从几分钟到几秒（快两个数量级）；CI 省下 25% CPU；每层缓存命中率 >99%
- Claude Mythos Preview 重写导入管道：内存省 20 倍，速度快 4 倍

## 问题：git 为什么扛不住

- git 是去中心化设计，每个克隆都是完整仓库、可离线工作；但他们实际像大多数公司一样把 git 当中心化系统用，而且客户端几乎都是本来就在线的 agent 和任务。
- 浅克隆、稀疏检出、promisor remote、内部镜像、blob 存储里的仓库快照（seeds）都用过：能拖时间，但合并速度一上来，快照离 main 越来越远，在部分克隆上维持 diff/blame 越来越费劲，镜像也撑不住磁盘和内存上限。

## 设计原则（参考了 Google Piper、Meta Sapling）

- **客户端永远在线**：数据需要时再拉。
- **客户端/服务端不对称**：历史、blame、提交、合并、rebase 都在服务端做；客户端只维护有限的本地缓存、铺工作文件、监控文件改动。
- **源码管理即服务**：客户端用到的查询全都开放 API，很多任务根本不需要本地仓库（自动 bisect、自动回滚流水线靠这个才可行）。
- **全部水平扩展**：任何地方（包括服务端）都没有完整的仓库副本，没有 packfile，不需要仓库维护。
- **提交便宜、增量、无锁**：成本随改动大小而不是仓库大小增长；除 main 和发布分支外不鼓励用 refs，避免全局共享状态。
- **工作副本可选、天然稀疏**：能走 API 就不检出；需要文件时用稀疏检出或虚拟化检出，读多少付多少。

## 架构

- **Changeset**：写前日志里的一条记录，存相对第一父提交改了哪些文件 + 指向 blob 存储里压缩内容的内容寻址指针；服务端创建，即时全局可见。移动 ref 只是对一行 Spanner 做 compare-and-swap，与创建 changeset 分开。
- **派生数据（derived data）**：blame、路径历史、提交图跳表等都由同一套递归机制从父节点的值算出；可选择预先算或延迟算；客户端看不到内部结构，可以随时加新索引（如复制检测、按路径搜文件）。
- **服务端**：一小组 Scion 服务器，本质是能现算派生数据并写回 Spanner 的大缓存；数据内容寻址、不可变，任何服务器都能缓存，几乎不需要协调。
- **拉取协议**：客户端 `scn` 不告诉服务端自己有什么，只按需求从根树递归请求缺的树和 blob；每个请求都是不变对象，任何缓存都能回答，可断点续传，天然支持稀疏和虚拟化检出。
- **三级缓存**：节点级 `scion-daemon`（从定期快照起步）→ 区域级 `scion-cache`（内存直出、无需计算差量或压缩）→ 权威 `scion-server`（读 Spanner/云存储）。三级 RPC 一致，但严格分层以隔离故障域。

## 经验教训

- **小团队快速开发会更常见**：过去这类系统要很多工程师、迁移好几年。
- **工程师的工作在变**：团队成员都认为 Claude 写代码比自己强，但人负责系统间关系和设计取舍，常常要对 Claude 说"不"——比如阻止靠线性扫提交日志来查合并时间这种违反约束的做法，或拦住对抗式审查引出的过度防御、过度设计。人仍审每个变更，但看意图而非逐行读。
- **质量和优化更好**：为所有重要交互做了封闭仿真、模糊测试、限流；Claude 还顺手找到祖先查询漏用索引这类优化。
- **安全**：支持目录级权限；审查工具能区分只改注释和敏感逻辑改动，让人聚焦关键改动。
- **运维**：用 Claude Tag 在 Slack 频道里给每个组件配一个盯盘的 Claude（"superfan"），能发现传统告警发现不了的细微异常。
- **重想旧假设**：agent 规模下全局锁式 merge queue 不现实，改为合并后、部署前自动测试；并发冲突由 Claude 快速修复。

## 对行业

- Scion 不适合当通用 git 替代品，只适用于超大 monorepo；它需要配套的审查、搜索、CI，难以对外提供。
- 他们预计 6–12 个月内这类问题会普遍出现，建议把思路带回 git：服务端架构可以和客户端不同、提供完整的服务端 RPC（甚至跨平台标准化）、改进协商协议、让 sparse/shallow 功能更好地组合；希望和 GitHub、GitLab、开源社区合作。

## 我的思考 / 为什么重要（以下为个人评论，非原文）

- 这是"AI 写代码规模化"少见的硬数据：4 个月 12 倍，瓶颈正从写代码转向审查、CI、合并和基础设施。
- 受益方向可能在开发者基础设施：代码托管、CI、代码审查、可观测性都得为 agent 重做。
- "人审意图、不逐行读"和"合并后测试、冲突交给 AI 修"是对传统工程流程的明显改写，值得持续跟踪其他公司是否跟进。
