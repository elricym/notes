### [DDOG 3Q26: Constructive Checks, Enterprise AI Supports Core Demand and Consolidation Gains](https://fundaai.substack.com/p/previewddog-3q26-constructive-checks)
**FundaAI**（财报前瞻，邮件有完整摘要和前两位渠道专家，在「Channel Expert C — North American Reseller」处截断）

- **总体判断**：3Q26 形势仍然积极。重复渠道调研显示需求健康，部分出现加速、超计划；老客户扩张改善，新客户一开始就买更多模块；企业 AI 部署带来基础设施监控、应用追踪和日志的额外需求，客户整合分散工具、从老平台迁移也在让 DDOG 拿份额。
- **AI 原生客户**：调研显示最大 AI 客户在续约和指引重置后用量已企稳并恢复增长，支撑来自它的 ARR 回升，但确认收入有滞后、初期还会下降。其他 AI 原生客户的训练需求支撑 4Q 动能，另一家大型 LLM 客户在放缓。预算纪律、日志优化和合作伙伴执行不均仍是变量。
- **数字预期**：3Q26 收入同比增长 36%，超指引 5–6 个百分点，符合买方预期；4Q26 收入指引上限对应同比 30–31%，在基数难度高约 3 个百分点的情况下，等于暗示环比增长稳定。
- **渠道 A（全球 GSI）**：2Q26 最终增长 34.2%，3Q26 初步加速到 34.6–34.8%，强在传统可观测性产品线、尤其是日志，而不是靠某个新产品；4Q26 预计 34–35%，1H27 初步区间 32–36%（未定）。
- **渠道 B（欧洲集成商）**：3Q26 增长约 25%，高于 20% 的预期（2Q26 约 20%）；老客户支出增速从上半年 8–10% 升到 12–15%；新客户更多从两三个模块起步。4Q26 预计约 25%，2027 年起始预测 30%，专家个人上行看法接近 35%，支撑来自扩张和整合，而不是 Bits AI 立刻贡献大量收入。

## 工程产品

### [AI SRE: what is it, how could it change on-call – and does it work?](https://newsletter.pragmaticengineer.com/p/ai-sre)
**Gergely Orosz · The Pragmatic Engineer**（深度文章，邮件在第 4 节「Making agents accurate」处截断，准确性、速度和成本、自主 agent 时间表以及对值班工程师的影响只看到了开头目录）

- **为什么现在火**：可靠性公式 i = c × p（事故率 = 变更频率 × 单次变更出错概率）。AI agent 让几乎所有科技公司的 PR 频率一年翻倍，Rootly 数据显示告警比一年前多，非工作时间告警接近翻倍。降低 p 有两条路：部署前更好的验证，以及从事故中学习，AI SRE 厂商主要做后者。
- **背景**：2025 年 5 月微软 BUILD 上演示的 Azure SRE Agent 从告警到发修复全程无人介入，作者当时觉得不真实，此后一年也没再听到。最近重新出现：OpenAI 做了内部的 Sevbot，ING 银行在自建，会场上 AI SRE 展台变多。本文采访了 Rootly、incident.io 和 ResolveAI（作者投资了 incident.io）。
- **AI SRE 主要帮的是调查阶段**：看告警、查仪表盘、翻 runbook、搜日志。incident.io 的编排器像值班工程师开八个标签页一样，把调查分给子 agent。值班工程师在告警后约五分钟进到事故频道就能看到 AI 的调查摘要，省掉「铲土」工作。
- **信任是自建的主要原因**：agent 要看遥测、日志甚至代码仓库，公司越大越不愿把敏感数据给外部厂商，即使对方承诺零数据保留。作者的判断是专职做这件事的厂商长期可能比自建更强，因为大公司里这往往是工程师很快就失去兴趣的副业项目。
- **只缓解还是也修根因**：incident.io 把事故上下文交给工程师已有的编码 agent（客户更喜欢自己的编码环境）；ResolveAI 自己写简单 PR、大改动交给客户的 agent；Rootly 的目标是一个 agent 起草 PR、另一个判断能否安全合并后自动合并，但目前所有 PR 仍需人批准。
- **调查 agent 的演进**（ResolveAI 两年三套架构）：2024 年脚本化流程，遇到不按剧本的事故就不行；2025 年单 agent + 知识图谱，出现上下文腐烂、自我确认（几乎总是确认第一个猜测）和没有记忆的问题；2026 年改为多 agent：调查者、结构上独立的验证者、负责通报的沟通者。
- **典型流程**：触发 → 定位（看最近的部署和特性开关）→ 并行展开 → 验证 → 在 Slack 汇报 → 工程师在 Slack 里引导 → 交给工程师或编码 agent 执行缓解。每一步都要在延迟、准确性和成本之间取舍。
- **上下文层**：三家都做了知识图谱 + 记忆 + 工具（Rootly 叫 Atlas，incident.io 叫 Nexus，Resolve 叫 HiveMind）。Rootly 的记忆有「激活」和被反驳后「隔离」两种状态，并且是唯一允许客户选择共享脱敏事故数据的厂商；联合创始人 JJ Tang 说「一次 Redis 配置错误引起的故障不是商业机密」。作者认为可以受益，但贡献数据前要先把机密洗干净。
- **在 Slack 里说多少话**：incident.io 发现太简短工程师不信任，太长又烦；Rootly 的 agent 默认安静，只在问题没人回答、有人没上下文就加入、有人没证据就宣布「已缓解」、或宣布高风险操作却没有回滚方案时才发言。
- **自建案例**：Monzo 的通用工程 agent「Agent Chip」有事故模式；OpenAI 的 Sevbot 收集信息、提出缓解方案但从不自己执行，被指示后才执行；Stripe 每次故障都跑调查 agent，简单版平均 3 分钟、深度版平均 14 分钟；Google SRE 在 Gemini CLI 里用 ProdAgent，不生成代码，只建议调用 MCP 暴露的工具（如 borg_task_restart），带策略约束和审计记录。
